## 二、实施中踩的坑（含解法）

1. **npm 不回退查找上级 .npmrc**：只在 cwd 找。`payload/app`、`shell` 必须各自放 .npmrc（registry + cache），否则回落不可达的 npmjs 挂死（表现为"无输出挂起"）。
2. **`~/.npm` 缓存被 root 污染**（EPERM）：无 sudo 时用项目内 `.npm-cache/` 独立缓存绕开。
3. **Tauri bundle.resources 的 glob 不支持 `..` 前缀**（glob crate 0.3.4 把 `..` 当字面目录名，永远匹配不上）：在 `shell/src-tauri/payload` 建指向 `../../payload` 的符号链接，资源模式全部落在 src-tauri 内。符号链接已入库。
4. **macOS `node:fs` `rmSync recursive` 偶发 ENOTEMPTY**：assemble 脚本改用 shell `rm -rf`。
5. **tao 不装 SIGTERM 处理器**：直接 SIGTERM 壳进程会跳过 `ExitRequested`，dsh 变孤儿。用 `signal-hook` 接管 SIGTERM/SIGINT，先清进程树再退出（DESIGN §2.2 退出路径的补强）。
6. **从受限 shell 启动 GUI 会误报"崩溃"**：沙箱派生的 WebContent 无法 XPC 查 launchservicesd（`CRASHSTRING rdar://28724618`）→ WebPage close → 应用退出且无任何 stderr。用 `open`（LaunchServices）启动完全正常。**调试 GUI 应用务必用 `open`，不要从受限 shell 直接跑二进制。**
7. **create-dmg 的 AppleScript 美化需要 Finder 自动化权限**：headless/受限环境必失败。

## 三·五、GitHub CI 修复实录（2026-08-15 晚间）

推送到 `minzojian/dsh-desktop`（public）后 5 轮修复：

1. **npmrc 绝对 cache 路径破坏 CI**：`cache=/Users/kent/...` 在 runner 上不可创建 → 移除，改为 assemble 显式 `--cache` + shell/.npmrc 相对路径（按 cwd 解析，CI 上落到 workspace 根）。
2. **job 级 env 用 `${{` runner.temp `}}` 无效**：runner context 仅 step 级 env 可用 → 删掉（冗余）。
3. **Windows 上 `spawnSync("npm")` 失败**：npm 是 `npm.cmd` 批处理，spawn 无法直接执行 → `shell: true`（仅 win32）。
4. **PowerShell junction 的 -Target 必须绝对路径**：`..\..\payload` 被拒 → 用 `${env:GITHUB_WORKSPACE}` 拼绝对路径。
5. **Windows 打包目标**：基础配置 `targets=["app"]` 是 macOS 语义 → `tauri.windows.conf.json` 平台专属深合并为 `["msi","nsis"]`。

经验：GitHub Actions 匿名 API 限流 60 次/小时，排查期很快就烧完——页面抓取（`github.com/.../actions/runs/<id>` 服务端渲染）是可靠的替代。

## 三·六、为什么 payload 不用 pnpm（2026-08-16 实测论证）

DSH 源码仓库用 pnpm 是**源码 monorepo 开发流程**（`pnpm install && pnpm run build`），我们消费的是**发布版 npm 包**，两者无关。实测 pnpm 11.7 装同一 `@deepseek-ai/dsh@0.1.0-rc.6`：

| 项 | npm（现用） | pnpm 11 |
|---|---|---|
| 安装耗时（暖缓存） | ~10s | ~17s |
| node_modules 布局 | 真实文件树 | 符号链接 + .pnpm store |
| 构建脚本 | 全部执行 | **默认屏蔽**（ERR_PNPM_IGNORED_BUILDS：node-pty/koffi/subprocess-local 等 5 个） |
| 原生模块 | 直接可用 | 当前 rc.6 恰自带产物侥幸可用，但依赖屏蔽脚本的包会**静默损坏** |
| 平台定位（--os/--cpu） | 直接支持 | 需 `supportedArchitectures` 配置 |
| 瘦身脚本/资源打包 | 直接遍历 | 符号链接布局需改造 |

结论：**payload 保持 npm**。pnpm 的 workspace/store 优势在"单包生产安装+打包分发"场景无收益，反而引入构建脚本屏蔽、符号链接布局、平台定位配置三个新风险点。若将来在本地开发/改动 DSH 源码（策略 B），开发环境跟随官方用 pnpm 即可，与产物组装无关。
